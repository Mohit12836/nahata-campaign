## 3. Evidence-based findings

### F-01 — Admin auth defaults do not fail closed (Critical)
**File:** `src/lib/auth-server.ts`  
`getAdminSessionSecret()` returns a hardcoded fallback when the environment secret is missing/weak; `getExpectedAdminPin()` returns a hardcoded default PIN when environment configuration is missing. These behaviors conflict with the same repository's test suite Group 11, which expects missing production configuration to return `null` and reject the default PIN. The current source and test expectation disagree.  
**Gate:** missing/weak production secrets must deny login and token generation; configured strong secret/custom PIN must pass; tests must prove both.

### F-02 — Public coupon SELECT policy is unrestricted (Critical)
**File:** `supabase/migrations/20261010_nahata_campaign_schema.sql`, approximately lines 145–147.  
The policy named `Public can verify own coupon by code` currently uses `for select using (true)`. This policy does not scope reads to a caller's coupon. It can expose all rows allowed by that table policy to roles granted table SELECT. Confirm actual grants and deployment configuration, then replace public direct table reads with a server-mediated, minimal-field verification path or an appropriately scoped design.  
**Gate:** anonymous role cannot enumerate coupon/customer PII; coupon verification returns only minimum fields for the supplied code.

### F-03 — Prize selection fallback can award exhausted stock (High)
**File:** `src/lib/store.ts`, `selectWinningPrize()`.  
If no active in-stock prize exists, selection falls back to active prizes including exhausted ones; if no active prizes exist, it falls back to all prizes. The local claim flow may therefore issue a coupon for unavailable inventory.  
**Gate:** no eligible prize returns a clear unavailable result; no coupon is created and inventory is never oversold.

### F-04 — Persistence and atomicity are not reliable in serverless execution (High)
**Files:** `src/lib/store.ts`, `src/lib/customer-auth.ts`, `src/app/actions/campaign.ts`.  
Business state uses in-memory stores and browser `localStorage`; customer sessions are held in a process-local Map. These are not durable/shared across separate serverless instances. Supabase RPC is attempted for claims, but a local fallback is used when Supabase is not configured.  
**Gate:** production mutations must require the central database; claim and redemption must be atomic/idempotent; missing database configuration must fail closed rather than silently switching to volatile state.

### F-05 — Tenant isolation must be checked through the server-action boundary (High)
**Files:** `src/app/actions/admin.ts`, `src/lib/supabase-server.ts`, `supabase/migrations/20261012_vismart_multitenant_cinderblock_rls.sql`.  
The visible admin customer/coupon queries do not apply explicit merchant scope. The server client prefers `SUPABASE_SERVICE_ROLE_KEY` when configured, and service-role access bypasses RLS; therefore RLS policies alone cannot prove tenant isolation for these queries.  
**Gate:** all server actions authorize the merchant scope explicitly; cross-tenant read/write tests prove isolation with the actual privileged-client path.

### F-06 — Existing concurrency test is only a simulation (High)
**File:** `scripts/test-suite.ts`, Group 4.  
The concurrency check is a synchronous loop that decrements a local number; it does not send concurrent database claims or prove SQL locking/transaction behavior.  
**Gate:** run parallel claims against a disposable/staging database and assert successful claims never exceed stock, duplicate phone claims are idempotent, and duplicate redemption is rejected.

### F-07 — Test command and CI evidence are missing (Medium)
**Files:** `package.json`, `scripts/test-suite.ts`.  
The suite exists but no npm test script is defined. The source contains a production fail-closed test expectation inconsistent with `auth-server.ts`. No successful build/lint/test run has been performed during this connector audit.  
**Gate:** documented deterministic test command; lint, typecheck, unit tests, build, and migration/DB checks run in CI with recorded results.

### F-08 — Campaign and customer-consent behavior needs review (Medium)
**Files:** `src/app/actions/campaign.ts`, `src/lib/store.ts`, campaign funnel components.  
The action validates `input.consent === true`, but the local store hardcodes `whatsapp_consent: true`. The funnel passes `consent: true` from its submit handler. Consent should be an explicit customer choice and recorded accurately, with separate consent for marketing where required.  
**Gate:** no inferred consent; persist the actual consent choice and timestamp; distinguish offer processing from optional marketing messaging.

## 4. Existing tests: interpretation
A file named `scripts/test-suite.ts` contains many assertions, but its existence is not proof of execution. The "concurrency" and "share gate" tests use local simulation functions; they do not prove browser automation, durable persistence, live WhatsApp delivery, or database concurrency. Group 11 expects fail-closed auth semantics that the current source does not implement. Test execution remains **NOT RUN** in this connector session.
